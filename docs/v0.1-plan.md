# v0.1 build plan

v0.1 is the smallest release that is genuinely useful: sync Search Console, crawl the site, run about 30 checks across indexing, redirects, hosts and search performance, and answer "what's wrong?" in Claude Desktop. Everything else in the spec waits for later versions.

## In scope

- `npx` CLI with `init`, `sync`, `crawl`, `audit`, `mcp` commands
- Config file with zod validation; empty key = service off
- SQLite database, migrations, resumable job runner
- Google Search Console: OAuth, property selection, 16-month backfill, daily incremental sync
- Static HTML crawler (no JS rendering) with robots.txt, sitemaps and hop-by-hop redirects
- Check engine, ranking (clicks × yield × certainty ÷ effort), severity floor, finding diffs between runs
- 31 checks (table below)
- MCP server with four tools
- README with setup for Windows and macOS

## Out of scope for v0.1

Dashboard UI, HTML report export, CrUX/PSI, logs, GA4, Bing, provider adapters, JS rendering, fix verification, change monitoring, annotations, Docker. The schema must not block any of these.

## Milestones

| # | Milestone | Done when |
| --- | --- | --- |
| M0 | Scaffold | Repo builds on Windows and macOS; lint, types and Vitest run in CI; `npx . --help` works |
| M1 | Config, database, jobs | `init` writes a config; migrations create all v0.1 tables; a job killed mid-run resumes from where it stopped |
| M2 | Search Console sync | `sync` backfills 16 months for one property, then syncs incrementally; anonymised-query share is stored per day |
| M3 | Crawler | `crawl` handles 10,000 pages, records every redirect hop, robots.txt and sitemap membership, and resumes after interruption |
| M4 | Check engine + 31 checks | `audit` runs all checks, skips any missing capability cleanly, ranks findings, and marks each new, persisting or resolved |
| M5 | MCP server | Claude Desktop can call all four tools after adding the config entry and restarting |
| M6 | Release | Dogfooded on kupka.ca and the fixture site; README complete; licence chosen; published to npm and GitHub |

## Schema (v0.1 tables)

| Table | Holds |
| --- | --- |
| `properties` | Site URL, GSC property, brand terms |
| `gsc_query_page_daily` | search type, date, query, page, clicks, impressions, position |
| `gsc_page_daily` | search type, date, page, clicks, impressions, position (totals, including anonymised queries) |
| `gsc_sync_state` | One row per synced day: row counts, row-cap hit, anonymised-click share. Last synced date is the latest row |
| `crawls` | Crawl id, start/end, settings, status |
| `pages` | Per crawl: URL, status, content type, title, H1, meta robots, X-Robots-Tag, canonical, word count, depth, indexable flag, in-sitemap flag, body hash |
| `redirect_hops` | Per crawl: URL, hop number, status, target |
| `links` | Per crawl: from, to, anchor, nofollow, location (nav/body/footer when detectable) |
| `robots_rules` | Per crawl: user agent, allow/disallow rules, sitemap lines |
| `sitemap_urls` | Per crawl: URL, sitemap file, lastmod |
| `check_runs` | Run id, snapshot, check versions |
| `findings` | Run id, check id, key, status, value at stake, certainty, effort, priority, summary, fix asset |
| `finding_evidence` | Finding id, evidence refs |
| `finding_lifecycle` | Finding key, state, dates, effort override (created now, used from v0.2) |
| `jobs` | Type, payload, state, checkpoint, attempts |

## MCP tools in v0.1

| Tool | Does |
| --- | --- |
| `whats_wrong` | Top findings, severity floor first, with optional category filter and limit |
| `explain_finding` | Full detail, evidence and fix asset for one finding |
| `audit_status` | Last sync, last crawl, last audit, skipped checks and why |
| `run_audit` | Queues sync, crawl and audit as jobs; returns progress |

## Testing

- **Fixture site.** A small local site in `test/fixtures/broken-site/` with one deliberate fault per check, plus a clean twin. Every check has a test against both.
- **Seeded GSC data.** Synthetic `gsc_*` rows for performance checks, including a brand-masked decline and a cannibalised query.
- **Dogfood.** Run against kupka.ca before release and review every finding by hand for false positives.

## Known constraints to design for

- **Search Console row cap.** The API caps the rows it returns per day per property. Detect and record when a day hits the cap, and lower certainty on query-level findings for those days.
- **Anonymised queries.** Page totals exceed the sum of query rows. Store both and report the gap.
- **Data lag.** Search Console data trails by a few days. Never treat the latest days as a decline.
- **Redirect capture.** Turn off automatic redirect following in the crawler's HTTP client and record each hop explicitly.
